## 2. 用户必须完成的官方准入

按以下顺序处理，前一步未完成时不要提交后一步：

1. 联系闲鱼业务运营，说明要以企业服务商身份接入小程序和虚拟订单，取得定向邀请及对接人。
2. 使用签约企业主体注册淘宝企业账号，同步创建并实名企业支付宝账号。
3. 用该企业账号进入[淘宝开放平台](https://open.taobao.com/)，完成开发者实名认证和业务身份入驻。
4. 如果没有“阿里生态API开发”，在[业务身份申请入口](https://work.open.taobao.com/open-console-enter)申请“应用软件开发商”或闲鱼开发者身份。
5. 申请“闲鱼垂直行业-C端”AppKey；因需要订单能力，同时申请“闲鱼垂直行业-B端”AppKey。
6. 确保淘宝开放平台主体、闲鱼入驻主体和合同签约主体完全一致。
7. 回到[闲鱼三方开放平台](https://open.goofish.com/#/appList)，使用签约企业所有的闲鱼账号填写申请；不要使用现有个人卖家账号提交正式申请。
8. 由闲鱼运营回填 C/B AppKey，再申请本文第 6 节的最小权限。
9. 按闲鱼要求开通聚石塔；需要访问 Oracle JIYU 时申请奇门出站审批。
10. 完成合同、保证金、ICP备案、隐私政策、自测、双端截图、客服接入和发布审核。

## 4. MRD：市场与业务需求

### 4.1 用户问题

- 当前闲鱼个人卖家链依赖浏览器登录态、Cookie、验证码和页面结构，无法提供稳定的官方订单消息、发货状态和退款同步。
- 用户购买数字额度后不应再联系卖家、选择第二个系统或自行封装工具；从付款到获得兑换码应在同一订单上下文完成。
- 卖家需要按面额销售，但不应把 807 张兑换码逐张发布为商品，也不应维护第二份明文卡池。

### 4.2 目标用户

- 需要使用 JIYU AI 文本或生图 API 的个人开发者和小团队。
- 已理解购买的是 JIYU AI 额度兑换码，而不是 OpenAI、Anthropic 或其他平台账号的用户。

### 4.3 业务目标

- 把闲鱼作为与链动小铺并列的购买入口，Sub2API 继续作为库存、兑换、余额和账本唯一事实源。
- 付款后自动完成一次且仅一次的兑换码预留和展示；重复消息、刷新、回调重放不得重复出库。
- 订单关闭、退款、发货和兑换状态可对账，异常订单进入人工补救，不对买家重复发送消息。

### 4.4 非目标

- 不销售或交付第三方平台账号、共享登录态、Cookie、订阅地址或上游密钥。
- 不把闲鱼买家个人信息复制到 Oracle，不新建第二库存或第二账本。
- 不绕过闲鱼审核、验证码、合同、保证金、类目或聚石塔/奇门要求。

## 5. PRD：产品与履约流程

### 5.1 商品与规格

- 首选官方推荐的“一个通用闲鱼商品 + 小程序内商品目录”。
- 商品目录提供 `1/10/30/50/100/300/500/1000` 八个固定面额；如运营要求使用 SKU，则每个 SKU 独立价格和可售数量。
- 前台库存来自 Sub2API 的可用兑换码聚合，展示为有限库存或售罄，不把兑换码明文同步到闲鱼。

### 5.2 用户流程

1. 用户从通用商品进入 JIYU AI 小程序，选择面额并确认服务说明、有效期和退款条件。
2. 小程序创建闲鱼订单并拉起官方支付。
3. 服务端收到订单状态消息后调用订单查询；只有官方状态确认已付款、金额和面额一致时才进入履约。
4. 聚石塔服务通过获批奇门调用把订单哈希、面额和请求幂等键发送给 Oracle 低权限适配器。
5. Sub2API 在事务内按面额锁定一张未使用兑换码；同一订单重复调用返回同一张，不再次扣减库存。
6. 小程序订单页面展示兑换码和“一键复制”，并明确兑换入口、有效期和售后规则。
7. 展示成功后调用官方虚拟发货接口标记该订单已发货；接口本身不承担卡密分配。
8. 用户在 JIYU AI 兑换后，Sub2API 回写兑换状态；退款和关闭消息进入同一订单对账流程。

### 5.3 订单状态

```text
created -> paid_verified -> reserved -> presented -> virtually_delivered
   |            |              |             |
closed       review          retry        redeemed
   |            |              |             |
refunded <------+--------------+-------------+
```

- `paid_verified` 之前禁止领码。
- `reserved` 之后重复消息只能读取原预留，不得分配新码。
- 兑换前退款按平台规则释放或作废预留；兑换后退款必须进入人工审核，防止已消费额度重复退款。
- 平台发货标记失败时保留原预留并重试标记，不重新领码。

### 5.4 用户体验

- 从选择面额到获得兑换码不超过一个小程序流程，不要求用户联系客服或安装 MCP。
- 订单页只显示必要状态：待支付、处理中、已交付、兑换成功、退款处理中和需要人工处理。
- 明确展示购买对象是 JIYU AI 额度兑换码、面额、有效期、退款边界和客服入口。
- 不把系统内部的 Frist、CC 中转、Sub2API、渠道或上游供应商名称暴露给普通用户。

## 6. 最小权限申请

### 6.1 TOPAPI

首期仅申请：

- `orderCreateTopApi`：创建订单。
- `orderQuery`：校验付款状态、金额和 SKU。
- `orderVirtualDelivery`：交付成功后逐单标记虚拟发货。
- `orderClose`：发货前关闭异常订单。
- `refundQuery`：查询退款状态。
- `partRefundBySeller`：按批准规则执行部分退款。
- `refundBySellerAfterSendGoods`：发货后全额退款。

首期不申请实物物流、手机号、地址、位置、相册、麦克风或其他与额度兑换无关的权限。

### 6.2 Windvane 与消息

- 首期申请 `tradePay` 拉起官方支付。
- `clipboard` 只有订单页确需原生“一键复制”且普通 Web 能力不足时再申请。
- 订阅 `idle_autotrade_OrderStateSync` 和 `idle_autotrade_RefundSync`；消息只作为触发，最终状态以 `orderQuery` 回读为准。

## 7. 技术架构和数据边界

```text
闲鱼小程序 / 官方订单消息
          |
          v
聚石塔订单适配器 -- orderQuery / virtual.delivery / refund
          |
      奇门审批出站
          |
          v
Oracle 低权限履约适配器
          |
          v
Sub2API 原子预留 -> 兑换 -> 余额与账本
```

- 聚石塔保存闲鱼原始订单和用户信息；Oracle 只接收不可逆订单哈希、面额、状态和幂等键。
- Oracle 返回本订单的交付凭证，不获得买家昵称、手机号、地址或其他非必要身份信息。
- 现有 `xianyu_redeem_reservations` 继续承担订单哈希到兑换码的唯一映射，不新增卡池。
- 任何服务凭据只存聚石塔/Oracle 受保护的密钥设施，不进入仓库、日志、截图或申请材料。
- 卖家授权 token 过期前必须在既有运维日历提醒续期；不新建常驻 AI 管理面。

- ICP 及域名材料；小程序容器域名和第三方 H5 白名单按运营确认后填写。

- iOS/Android 自测截图、订单创建/支付/交付/退款测试结果和发布包。
- 平台要求的保证金；金额以实际类目和控制台提示为准，不预设或代缴。

## 9. 上线验收与失败关闭

- 仅在预发布环境用官方测试方式完成订单消息联调；不得在生产制造合成付款。
- 第一笔自然订单继续沿用一次性观察票：只发一张、自动暂停、回读预留/展示/虚拟发货/兑换全链。
- 订单金额或面额不一致、订单查询失败、库存不足、奇门不可达、展示失败时一律不标记发货。
- 官方链路通过前，现有个人卖家桥接不删除；通过后再按真实调用关系替换浏览器订单监听和点发货环节。
- 官方链路替换的是平台入口，不替换 Sub2API 的库存、兑换、余额和账本。
