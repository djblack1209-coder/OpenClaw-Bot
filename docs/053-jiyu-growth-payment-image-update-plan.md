# JIYU AI 生图、充值与自助更新执行方案

> 日期: 2026-08-08
> 领域: frontend / ai-pool / deploy / payment / docs
> 状态: 低风险项已执行；上游线路、支付发布和更新架构等待老板确认

## 一句话目标

让新用户按“注册或登录 → 充值 → 创建专用密钥 → 一键导入 CC Switch → 开启本地路由与用量查询 → 直接开始文本或生图调用”的顺序完成首次使用，同时保证上游品牌不外露、价格合同不漂移、更新不会覆盖 JIYU 定制改动。

## 当前基线

- 生产运行 `v0.1.172-jiyu.5`，创建密钥页同时展示 Claude 根端点和 ChatGPT `/v1` 端点，并默认勾选 CC Switch 导入。
- 10 个文本分组、10 个一对一渠道和 10 条监控已上线；监控按渠道A五条、渠道B五条排序，周期为 300 秒、抖动为 ±30 秒。
- Sub2API 已原生提供 `POST /v1/images/generations` 和 `POST /v1/images/edits`，并支持按分组限制生图权限、独立图片倍率和按分辨率计价。
- 本机 CC Switch 现存两个旧生图 MCP 记录，但启动命令指向的脚本已经不存在，不能视为可用能力。
- 链动小铺已有 7 档统一 JY Logo 商品草稿；平台规则禁止当前商品类型，全部保持下架、零库存，充值中心没有写入无效链接。

## Phase 1：生图渠道和专用密钥

### 建议方案

把两个上游生图入口匿名映射为：

1. `JIYU 生图 · 渠道A`
2. `JIYU 生图 · 渠道B`

每个入口使用独立上游凭据、独立账号、独立分组、独立渠道和独立监控。文本 Key 不自动获得生图权限；用户在“API 密钥”中另建“生图专用 Key”，只允许访问生图分组，降低泄漏后的费用风险。

### 落地前必须确认

- 两个上游是否都提供 OpenAI 兼容的 `/v1/images/generations`，还是其中一个为异步任务接口。
- 每个上游真实可用的模型名、分辨率、单图成本、并发数、超时和内容安全规则。
- 用户倍率继续采用“上游倍率绝对增加 `0.05x`”，还是图片按张定价。图片按张计费时不能直接套用文本倍率。
- 是否允许图片编辑、参考图、透明背景和批量生图；未验证的能力默认关闭。

### 验收标准

- 两个匿名生图分组均有独立真实监控，不复用文本监控，不显示上游名称或域名。
- 用专用 Key 调用 `/v1/images/generations` 能返回可解析图片；文本 Key 调用同一路径返回权限拒绝。
- 用量记录显示图片数量、尺寸、费用和对应匿名渠道；失败请求不扣成功费用。
- 上游超时、限流和内容审核错误在页面中如实显示，不用静态成功状态掩盖。

## Phase 2：CC Switch 与 MCP

采用“JIYU 生图 API + 本地 stdio MCP”组合：CC Switch 负责同步 MCP 到 Claude、Codex、Gemini、OpenCode 和 Hermes；MCP 只暴露 `generate_image` 工具并调用 JIYU 的 `/v1/images/generations`。

首版不把生图请求强塞进 Claude/ChatGPT 文本协议转换。CC Switch 的本地路由主要解决 Messages、Chat Completions 和 Responses 的文本格式转换，不能自动把普通对话变成独立生图工具。

安全约束：

- Key 只从本机环境变量或系统钥匙串读取，不写源码、教程、日志、命令行参数或截图。
- stdio MCP 不能向 stdout 打普通日志，避免破坏 JSON-RPC；日志只写 stderr，并做凭据脱敏。
- 只允许 HTTPS 的 JIYU 域名；拒绝任意 `base_url`、重定向到私网、超大响应和非图片内容。
- 首版只支持单图，设置请求超时、最大图片字节数和一次重试；批量能力单独验收后再开放。

小白操作说明见 `docs/087-jiyu-image-mcp-guide.md`。

## Phase 3：链动小铺充值

平台书面确认前维持现状，不发布、不补库存、不做真实付款、不回填草稿链接。获得确认后按以下顺序执行：

1. 只发布 ¥1 档，确认标题、类目、交付说明和售后条款通过审核。
2. 用真实买家完成一次 ¥1 购买，记录订单号但不在仓库保存个人信息。
3. 验证付款后交付兑换码或充值凭证，站内核销后余额只增加一次。
4. 验证退款、重复回调、超时和人工补单都不会重复入账。
5. ¥1 闭环通过后再逐档发布 ¥10/50/100/300/500/1000，并把真实公开商品链接写入充值中心。

后续闲鱼、U 支付等入口使用同一个“支付方式注册表”，充值中心按可用状态展示，不为尚未验收的入口放按钮。

## Phase 4：WebUI 一键更新

### 方案 A：CI 构建兼容包 + WebUI 安装（推荐）

CI 发现官方新版本后，在干净源码上应用 JIYU 补丁、运行聚焦测试、构建 ARM64 包并生成版本清单和 SHA-256。服务器只下载已通过门禁的 JIYU 包；管理员在 WebUI 点击更新后，由 root-only 安装代理完成备份、停服、替换、健康检查和失败回滚。

优点：生产机不编译、按钮可直接使用、不会被官方二进制覆盖品牌；缺点：需要新增 CI 发布工件和受限本机安装代理。

### 方案 B：生产机点击后现场构建

服务器拉取官方源码、应用补丁、安装依赖并现场构建。优点是没有外部工件仓；缺点是更新慢、生产机供应链和磁盘面扩大、补丁冲突时恢复更复杂。

### 方案 C：直接安装官方二进制后重新打品牌

不采用。运行时改设置只能恢复标题和 Logo，不能恢复密钥双端点、CC Switch 导入、监控排序等代码级定制。

建议选择方案 A。实施后 WebUI 必须显示“检查中、兼容包准备中、可安装、安装中、回滚中、失败原因”六类真实状态；不存在兼容包时按钮必须禁用并给出清楚原因，不能再次出现截断的 `status c`。

## 需要老板确认的三个决定

1. 生图价格：继续倍率加 `0.05x`，还是按每张图片固定加价。
2. 上游能力：授权先接两个匿名生图渠道的“文生图单图”，图片编辑和批量生图以后再开。
3. 更新架构：采用方案 A 的 CI 兼容包和 root-only 安装代理。
