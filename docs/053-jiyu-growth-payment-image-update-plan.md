# JIYU AI 生图、充值与自助更新执行方案

> 日期: 2026-08-08
> 领域: frontend / ai-pool / deploy / payment / docs
> 状态: 生图双渠道已建立但上游仍异常；专用私有 R2 和原生异步生图存储已落地；中央 MCP 已于 2026-08-11 退役

## 一句话目标

让新用户按“注册或登录 → 充值 → 创建专用密钥 → 一键导入 CC Switch → 开启本地路由与用量查询 → 直接开始文本或生图调用”的顺序完成首次使用，同时保证供货上游身份不外露、价格合同不漂移、更新不会覆盖 JIYU 定制改动。`Anthropic`、`OpenAI`、`Grok` 等模型/API 生态标签保留，匿名化只针对真实供货上游及域名。

## 当前基线

- 生产运行基于官方 `v0.1.173` 的 JIYU 受管构建，创建密钥页同时展示 Claude 根端点和 ChatGPT `/v1` 端点，并默认勾选 CC Switch 导入。
- 当前生产合同为 13 个活动渠道、10 条启用文本监控和 2 条按真实异常禁用的生图监控；监控设置已按用户要求切回 Sub2API 原生 V1 主动探测，不再用固定渠道数量判断就绪。V2 配置、水位和历史仅为回滚保留。
- Sub2API 已原生提供同步生图和 `POST /v1/images/generations/async`、`POST /v1/images/edits/async`、`GET /v1/images/tasks/{task_id}`，并支持按分组限制生图权限、独立图片倍率和按分辨率计价。
- 本机 CC Switch 的失效旧生图条目和后续中央 MCP 均已退役。原生支持异步图片 API 的客户端直接调用 Sub2API，不再向 Claude、Codex 或 OpenCode 注入额外工具。
- 已建立 `JIYU 生图 · 渠道A`、`JIYU 生图 · 渠道B` 两个 OpenAI 兼容生图分组、账号、渠道和监控配置；两条监控保存加密凭据和 300±30 秒合同，但在上游恢复前保持禁用。
- 渠道A上游标价为 `$0.05/次`，站内为 `$0.10/张`；渠道B高画质 `gpt-image-2` 为 `$0.07/次`，站内为 `$0.12/张`。渠道A请求返回 502、渠道B专用 Key 返回 401，均保留真实异常。
- Oracle 当前有 ¥1/10/30/50/100/300/500/1000 八档共 807 张未使用兑换码。Sub2API 原生 S3 备份与异步生图对象存储已使用 JIYU 专用私有 R2；首次备份已完成下载、校验和隔离恢复，图片前缀保持空，等待上游成功任务。

## Phase 1：生图渠道和专用密钥

### 建议方案

把两个上游生图入口匿名映射为：

1. `JIYU 生图 · 渠道A`
2. `JIYU 生图 · 渠道B`

每个入口使用独立上游凭据、独立账号、独立分组、独立渠道和独立监控。文本 Key 不自动获得生图权限；用户在“API 密钥”中另建“生图专用 Key”，只允许访问生图分组，降低泄漏后的费用风险。

### 当前落地口径

- 两个入口均按 OpenAI 兼容 `/v1/images/generations` 建立，但渠道A目前真实请求返回上游 502，渠道B令牌探测返回 401，需在上游后台确认密钥生图权限后再做收费单图验收。
- 用户生图价格固定为“上游单张价格 + `0.05` 美元/张”，不套用文本倍率；分组使用独立生图倍率 1x，避免绝对加价被倍率放大。
- 是否允许图片编辑、参考图、透明背景和批量生图；未验证的能力默认关闭。

### 验收标准

- 两个匿名生图分组均有独立监控配置，不复用文本监控，不显示供货上游名称或域名；上游恢复并完成一次受控单图验收后才启用周期监控，不能把未测状态伪造成绿色。
- 两个生图专用 Key 在上游后台授权成功后，用 `/v1/images/generations` 返回可解析图片；文本 Key 调用同一路径继续返回权限拒绝。
- 用量记录显示图片数量、尺寸、费用和对应匿名渠道；失败请求不扣成功费用。
- 上游超时、限流和内容审核错误在页面中如实显示，不用静态成功状态掩盖。

## Phase 2：原生异步 API 与对象存储

Sub2API 的异步生图接口和对象存储负责任务持久化与图片交付：任务完成后把大图片上传到 S3/R2/OSS/MinIO，只在 Redis 保存短任务状态和 URL，客户端通过任务 ID 轮询。原生支持该 API 的客户端直接提交 `/v1/images/generations/async` 并轮询 `/v1/images/tasks/{task_id}`，无需 MCP。

异步生图对象存储使用 JIYU 专用私有 R2，并复用原生备份 S3 凭据但隔离为 `images/` 前缀；图片 2 天删除、预签名 URL 24 小时，数据库备份使用 `backups/` 前缀并保留 7 天/最多 8 份。当前渠道 A 为权限拒绝，渠道 B 未提供 `gpt-image-2`，因此只等待上游恢复后做一张低质量验收，不增加周期性付费探针。

2026-08-11 调用关系复核确认中央 stdio MCP 没有生产服务调用者，只给三个本机客户端增加配置与故障面，因此已在受保护备份后移除。CC Switch 的文本协议路由不会自动把普通对话转成生图工具；不再为掩盖这一产品边界维护额外 MCP。需要图片时，由明确支持异步图片 API 的客户端直接调用；不支持该 API 的文本客户端保持文本能力，不做隐式请求转换。

安全约束：Key 不写源码、教程、日志、命令行参数或截图；只允许 HTTPS 的 JIYU 域名；付费 POST 不自动重试；上游未恢复前不做周期性付费探针。

## Phase 3：链动小铺充值

当前八档商品各 1 个已发布并映射到 Sub2API 的 807 张兑换码，低权限适配器已按订单哈希和面额原子预留，不再使用遗留 SQLite 卡池；首单观察票已武装，禁止重复发布或制造测试付款。下一步按以下顺序执行：

1. 只发布 ¥1 档，确认标题、类目、交付说明和售后条款通过审核。
2. 用真实买家完成一次 ¥1 购买，记录订单号但不在仓库保存个人信息。
3. 验证付款后交付兑换码或充值凭证，站内核销后余额只增加一次。
4. 验证退款、重复回调、超时和人工补单都不会重复入账。
5. 用户已决定停止继续建设闲鱼销售链。现有商品由用户手动下架，助手和自动交付桥通过 OpenClaw App 的“智能体”页关闭；不再申请小程序或建设新适配器。

后续闲鱼、U 支付等入口使用同一个“支付方式注册表”，充值中心按可用状态展示，不为尚未验收的入口放按钮。

## Phase 4：WebUI 一键更新

### 方案 A：CI 构建兼容包 + WebUI 安装（推荐）

CI 发现官方新版本后，在干净源码上应用 JIYU 补丁、运行聚焦测试、构建 ARM64 包并生成版本清单和 SHA-256。服务器只下载已通过门禁的 JIYU 包；管理员在 WebUI 点击更新后，root-only 代理先备份并原子暂存，管理员点击重启后由独立 systemd 任务核对运行哈希和健康状态，失败自动回滚。

优点：生产机不编译、按钮可直接使用、不会被官方二进制覆盖品牌；缺点：需要新增 CI 发布工件和受限本机安装代理。

### 方案 B：生产机点击后现场构建

服务器拉取官方源码、应用补丁、安装依赖并现场构建。优点是没有外部工件仓；缺点是更新慢、生产机供应链和磁盘面扩大、补丁冲突时恢复更复杂。

### 方案 C：直接安装官方二进制后重新打品牌

不采用。运行时改设置只能恢复标题和 Logo，不能恢复密钥双端点、CC Switch 导入、监控排序等代码级定制。

建议选择方案 A。实施后 WebUI 必须显示“检查中、兼容包准备中、可安装、安装中、回滚中、失败原因”六类真实状态；不存在兼容包时按钮必须禁用并给出清楚原因，不能再次出现截断的 `status c`。

## 已确定的执行决定

1. 生图价格固定为“上游每张价格 + `0.05` 美元/张”；首版只开放文生图单图。
2. 生图只通过独立 Key 和专用分组使用；图片编辑、参考图、透明背景和批量生图继续关闭。
3. 更新采用方案 A：CI 兼容包、SHA-256 清单和 root-only 安装代理；WebUI 只触发固定代理，不接受命令或下载地址参数。
